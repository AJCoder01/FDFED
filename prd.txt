1. Executive scope and success definition
ServiceHub remains a non-retail services marketplace connecting customers with local service professionals. The product concept is sound; the delivery strategy changes. This term should prove that the team can turn the fragmented static portals into one coherent, modern, navigable, and believable product experience.
A single-page application does not mean a single screen. It means one React application with client-side routes, shared layouts and components, preserved navigation state, and no full-document reload between marketplace screens.
Non-negotiable term outcomes
1.	SPA architecture: One React application serves guest, customer, provider, Arbitrator and admin experiences through client-side routes.
2.	Consistent UI: Typography, color, spacing, buttons, forms, cards, tables, statuses, dialogs, toasts, empty states, and navigation come from one design system.
3.	Workflow completeness: The main marketplace journeys work end to end with realistic mock data, including success, empty, validation, conflict, and error states.
4.	Responsive and accessible: Every P0 screen is usable at mobile, tablet, and desktop widths and supports keyboard navigation, visible focus, labels, and readable contrast.
5.	Backend-ready boundary: React components consume a repository/API adapter so the later Express backend can replace mocks without rewriting pages.
6.	Scope discipline: The evaluated interface is marketplace-led. Formal arbitration, hearings, awards, and a public arbitrator portal are included here (However with respect to arbitrator workflows we will only have basic functionalities like customer, provider filing disputes, case being assigned to the arbitrator, arbitrator viewing evidences and giving ruling, all parties being notified of the ruling).. All other features and workflows of different actors will be meticulous, well planned, connected and well executed.

Revised product concept and actors
Product statement  ServiceHub is a trusted non-retail services marketplace where customers discover and book local professionals, providers manage listings and jobs, and platform operations maintain quality and resolve routine service issues and in case of a dispute between the customer and the provider, arbitrator reviews evidence and gives ruling and parties are notified.

Actor : Visitor / Guest	
Primary Goal : Understand the marketplace and find a suitable service.	
Required SPA capabilities : Landing; category discovery; search/filter/sort; service and provider detail; trust content; post-a-job request; customer/provider sign-up; preserve intent through login.

Actor : Customer
Primary Goal : Book, manage, and review a service with confidence.
Required SPA capabilities : Profile and addresses; saved services; booking wizard; mock payment state; booking timeline; cancellation/reschedule; notifications; review; support ticket and evidence UI.


Actor : Individual Provider
Primary Goal : Publish services and complete paid work efficiently.
Required SPA capabilities : Onboarding; profile and verification status; listing management; availability; job inbox; accept/reject/propose time; fulfillment timeline; earnings summary; reviews; support.

Actor : Platform Admin / Operations
Primary Goal : Run the marketplace and handle exceptions.
Required SPA capabilities : Overview; provider/listing moderation; categories; booking inspection; support ticket resolution; users; mock refunds; notifications; marketplace reports and settings.

Actor : Organization Provider
Primary Goal : Coordinate multiple professionals under one business.
Required SPA capabilities : Organization profile, team list, shared availability, job assignment, and performance summary after the individual-provider flow is stable.

Actor : Arbitrator
Primary Goal : Able to view records and evidences submitted by Customer and provider for a dispute. Able to schedule hearings and notify rulings and awards. 
Required SPA capabilities : Arbitrator profile, case numbers, case history, hearings schedule, awards/rulings history



Support is a permission area inside the admin experience, not a separate visual product. Payment is represented as a mock integration state, not a human actor or separate portal. Formal arbitrator is not part of this term's navigation, workflows, or demonstration.

Mandatory state coverage
Every routed feature must deliberately implement the states below. A screen is incomplete if it only renders the happy path.
49.	Loading: Initial loading and content-refresh loading, using skeletons that resemble the final layout.
50.	Empty: No records, no results after filters, and first-use onboarding, each with a useful next action.
51.	Validation: Inline field validation, form-level summary, disabled submit while invalid or submitting, and retained user input.

53.	Error: Recoverable failure with retry, unavailable/offline simulation, permission denial, and a safe generic fallback.
54.	Confirmation: Destructive or consequential actions require confirmation and plain-language consequences.

58.	Images have purposeful alternative text or are marked decorative; form errors are associated with fields and announced.
59.	Touch targets are comfortably sized, tables become cards or scroll within their own region, and sidebars collapse deliberately.
7. Frontend workflows and acceptance behavior
These workflows are the product backbone for frontend evaluation. Each workflow names the route path, visible interaction, required states, and the point at which the interface is considered complete. All behavior may use mock data during this term, but the experience must be honest and repeatable.


Workflow 1 — Guest discovery and conversion
Primary routes: / → /services → /services/:serviceId → /login or /signup
Goal: Help a visitor reach a trustworthy service choice and preserve that choice through authentication.
UI path: Search by need/location; apply filters; inspect results; open service detail; inspect provider, reviews, scope, price, policy, and available slots; select Book; sign in; return to the service and selected intent.
Required interface states: Hero/default, results loading, no matches, filters applied, service unavailable, auth required, invalid login, and restored intent.
Frontend acceptance: No full reload occurs, URL state is meaningful, and the visitor returns from login without repeating discovery.
Workflow 2 — Customer booking and mock checkout
Primary routes: /services/:serviceId → booking stepper → /customer/bookings/:bookingId
Goal: Create a believable booking without requiring a production backend or payment gateway.
UI path: Choose slot; choose/add address; add notes; review service and price snapshot; choose a clearly labeled demo payment method; confirm; show booking ID and next steps.
Required interface states: No slots, slot becomes unavailable, incomplete address, invalid fields, mock payment processing, mock payment failure, duplicate-submit prevention, and success.
Frontend acceptance: The booking appears in customer and provider mock views, all steps are keyboard usable, and refresh restores the mock record where appropriate.
Workflow 3 — Customer booking management
Primary routes: /customer/bookings → /customer/bookings/:bookingId
Goal: Let the customer understand and change an upcoming or active booking.
UI path: Filter booking history; open details; view provider, schedule, address, payment display, and status timeline; request reschedule or cancellation; confirm consequences; see updated timeline and notification.
Required interface states: Upcoming, active, completed, cancelled, empty history, prohibited action, alternative slots, mock refund outcomes, and retry.
Frontend acceptance: The interface explains who changed the booking, when, why, and what the visible money state became.
Workflow 4 — Completion, review, and support
Primary routes: /customer/bookings/:bookingId → review dialog or /customer/support/:ticketId
Goal: Close the marketplace loop and provide a simple resolution path.
UI path: Confirm completion or view completed state; submit one rating/review; alternatively report a problem, select issue type/severity, add description/evidence, submit, and follow the ticket timeline.
Required interface states: Review eligible/ineligible/already submitted, upload progress/failure, ticket draft/submitted/waiting/resolved, and reopened state.
Frontend acceptance: A completed booking can be reviewed once; a support ticket is visibly linked to the booking; arbitration language is absent.
Workflow 5 — Provider onboarding and verification display
Primary routes: /signup?role=provider → /provider/profile
Goal: Collect the frontend information needed for a credible provider identity and show verification progress.
UI path: Create account; complete identity/business profile, categories, service area, experience, and document placeholders; review; submit; show Draft, Submitted, Changes requested, Approved, or Suspended display state.
Required interface states: Multi-step progress, save draft, validation, upload placeholder, changes requested with reason, success, and restricted listing action while unapproved.
Frontend acceptance: The provider knows what is missing and what action is available; the UI never claims real KYC processing.
Workflow 6 — Provider listing and availability management
Primary routes: /provider/services; /provider/services/new; /provider/services/:serviceId/edit; /provider/availability
Goal: Let a provider define a clear, bookable service and demonstrate schedule control.
UI path: Create listing; complete scope, price, duration, area, images, inclusions/exclusions, and policy; preview; publish mock state; set weekly hours, lead time, buffer, and blackout dates.
Required interface states: Draft, validation, preview, published, paused, archived, empty listings, unsaved changes, conflicting availability, and successful update.
Frontend acceptance: Published services appear in public mock search with the same content and INR formatting; archived services cannot be booked.
Workflow 7 — Provider job acceptance and fulfillment
Primary routes: /provider/jobs → /provider/jobs/:jobId
Goal: Give the provider one clear job inbox and fulfillment timeline.
ENSURE CUSTOMER SETS TIMELINE AND DEADLINE
DEADLINE FOR BOTH SINGLE DAY (Like cleaning service) and multi-day (Renovation work)
UI path: Review request; accept, reject, or propose a time; view customer/service details allowed for fulfillment; start job; add progress/completion notes; complete; view earnings display.
Required interface states: No requests, new request, response deadline, accepted, reschedule proposed, in progress, completed, customer issue open, action disabled, and failure/retry.
Frontend acceptance: Customer and provider mock views show compatible statuses and timestamps, and every consequential action has confirmation.
Workflow 8 — Admin marketplace operations
Primary routes: /admin → providers/listings/bookings/tickets/categories/users/reports
Goal: Show that a business can operate the marketplace from the UI.
UI path: Open action-first dashboard; review provider/listing; approve, reject, or request changes with reason; inspect a booking; triage and resolve a ticket; record a mock refund outcome; manage categories; inspect reports.
Required interface states: Pending queues, no queue items, filters, detail drawer/page, reason required, success, permission denial, stale-data warning, and retry.
Frontend acceptance: The admin experience uses the same design system as customer/provider, centers on marketplace operations, and contains no hearing/award workflow.
Workflow 9 — Post-a-job request
Primary routes: /post-a-job → request confirmation → /customer/requests/:requestId (P1 detail)
Goal: Capture demand when catalog search does not fit the customer's need.
UI path: Enter category, location, description, preferred date, budget, and contact information; review; submit; show request ID and response expectation.
Required interface states: Draft, validation, submitting, success, duplicate submit, attachment error, and no-match outcome mock.
Frontend acceptance: The form is no longer a dead-end contact page and never implies a confirmed booking or guaranteed provider.
Workflow 10 — Global notifications and session behavior
Primary routes: All protected layouts
Goal: Make cross-role status changes understandable and keep the demonstration coherent.
UI path: Open notification center; mark one/all read; follow deep link; show role-aware profile menu; log out; return to public site; handle expired demo session and unauthorized route.
Required interface states: Unread/read, empty, loading, deep-link target missing, session expired, unauthorized, and logout confirmation where unsaved work exists.
Frontend acceptance: Notification links reach the correct route and the user never sees another role's private layout or actions.

Similarly please ensure new workflows are implemented for Dispute Resolution. 
Broad Dispute Resolution Workflow implementation :
Customer files a dispute case against concerned provider (or vice versa). provider is notified. An Arbitrator is assigned the case. Customer and providers uploads evidence records. Arbitrator views/downloads evidence documents. Schedules hearings if necessary. Arbitrator gives ruling for the case. Both parties are notified of the ruling. Case is closed.
